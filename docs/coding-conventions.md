\"---\ntitle: Coding Conventions & Standards\ntags: [conventions, standards, typescript, react, nextjs]\n---\n# PROBLEM\nKeine festgelegten Coding Standards führten zu inkonsistentem Code, fehlender Type-Safety und vielen kleinen Problemen im Code.\n\n# LÖSUNG\nDefinierung und Durchsetzung von Standards für das Spikeball-ELO-Projekt.\n\n# CODING CONVENTIONS\n\n## 1. GENERAL RULES\n\n### 1.1 TypeScript Configuration\n- **STRICT** mode muss aktiviert sein\n- `noImplicitAny` = `true` (niemals deaktivieren!)\n- Code muss ohne TypeScript-Fehler kompilieren\n- ` @ts-ignore` nur mit ausführlichem Kommentar warum zwingend nötig\n\n### 1.2 ESLint Configuration\n- KEINE Regeln global auf `\"off\"` setzen\n- Bei Ausnahmen: Spezifische Regeln anpassen, nicht alles deaktivieren\n- Console.log nur für Development (`console.warn` und `console.error` sind okay)\n- `any` Types sollten vermieden werden (ESLint-Error)\n\n### 1.3 File Naming\n- Components: PascalCase (`UserProfile.tsx`)\n- Hooks: kebab-case mit prefix `use-` (`use-auth.ts`)\n- Utilities/Lib: kebab-case (`date-utils.ts`)\n- API Routes: lowercase (`src/app/api/players/route.ts`)\n\n## 2. TYPESCRIPT\n\n### 2.1 Type Definitions\n- **NIEMALS** `any` verwenden ohne triftigen Grund\n- Interfaces immer über `type` für Objekte bevorzugen\n- Props explizit als Interfaces definieren:\n\n```typescript\n// ✅ GUT\ninterface UserProfileProps {\n  playerId: string;\n  showStats?: boolean;\n}\n\nexport function UserProfile({ playerId, showStats = false }: UserProfileProps) {\n  // ...\n}\n\n// ❌ SCHLECHT\nexport function UserProfile({ playerId, showStats }: any) {\n  // ...\n}\n```\n\n### 2.2 React Component Props\n- Für Props Interfaces immer benennen: `ComponentNameProps`\n- Required Props ohne default value\n- Optional Props mit `?` und Default-Wert\n\n## 3. REACT / NEXT.JS\n\n### 3.1 Client Components\n- `\"use client\"` nur wenn nötig (state, effects, event handlers)\n- Server Components bevorzugen für performance\n\n### 3.2 State Management\n- Einfacher State: `useState`\n- Komplexer State: Zustand oder React Query\n- Globaler State: React Query für API-Daten\n- Keine Prop Drilling für tief verschachtelte Komponenten\n\n### 3.3 Effects\n- Minimale Verwendung von `useEffect`\n- Datenladen über React Query, nicht über manual polling\n- Cleanup-Funktionen immer implementieren\n\n## 4. API ROUTES\n\n### 4.1 Structure\n- Konstante Fehlernachrichten (erreicht bessere UX bei Fehlern)\n- Try-Catch-Blöcke konsistent\n- Auth-Prüfung am Anfang jeder Route\n\n```typescript\n// ✅ GUT\nimport { NextRequest, NextResponse } from 'next/server';\nimport { getCurrentUser } from '@/lib/auth';\nimport { db } from '@/lib/db';\n\nexport async function GET(\n  request: NextRequest,\n  { params }: { params: { id: string } }\n) {\n  try {\n    const currentUser = await getCurrentUser();\n    if (!currentUser) {\n      return NextResponse.json({ error: \"Nicht authentifiziert\" }, { status: 401 });\n    }\n\n    const playerId = params.id;\n    // ...\n  } catch (error) {\n    console.error(`[API Error] ${request.method} ${request.url}:`, error);\n    return NextResponse.json(\n      { error: \"Interner Serverfehler\" },\n      { status: 500 }\n    );\n  }\n}\n```\n\n### 4.2 Error Handling\n- Immer konsistente Error-Typen zurückgeben\n- Fehlercodes sinnvoll (400: Validation, 401: Auth, 403: Permission, 404: Not Found, 500: Server)\n\n### 4.3 Logging\n- Nur `console.error` für echte Fehler\n- Debug-Logs nicht in Production\n- Verwende Logger wenn nötig, aber nicht console.\n\n## 5. DATABASE (PRISMA)\n\n### 5.1 Naming Conventions\n- Models: PascalCase\n- Fields: camelCase\n- Foreign Keys: `[resource]Id` (zB. `userId`, `playerId`)\n\n### 5.2 Query Optimization\n- Nur benötigte Felder selektieren (`select`)\n- `include` sparsam verwenden\n- Relationen statt Arrays (siehe Schema)\n- Avoid N+1 queries mit `include` oder `findMany` mit relation\n\n### 5.3 Schema Design\n- Cascade deletes für relations\n- Required fields wenn möglich\n- Nullability wenn wirklich nötig\n\n## 6. UI/UX STANDARDS\n\n### 6.1 German Translations\n- **WICHTIG:** Alle Umlaute korrekt verwenden (ä, ö, ü)\n- Konsistente Schreibweise (zB. \"Freundschaft\", nicht \"Friendship\")\n- Copy für Buttons kurz aber klar\n\n### 6.2 Components\n- Nutze die `@/components/ui/*` Bibliothek (shadcn/ui)\n- Konsistentes Styling über Props nicht inline-styles\n- Responsive beachten (mobile-first)\n\n### 6.3 Accessibility\n- Semantic HTML\n- Alt-Tags für Bilder\n- Labels für Formulare\n- Keyboard navigation\n\n## 7. GIT WORKFLOW\n\n### 7.1 Commit Messages\n```\nfeat: add user profile picture upload\nfix: correct friendship status check logic\ndocs: update api documentation\nrefactor: optimize player query\n```\n\n### 7.2 Before Commit\n- Test: `npm run build` muss erfolgreich sein\n- Lint: `npm run lint` sollte kritische Fehler zeigen\n- Type-Check: Optional per Script\n\n## 8. SECURITY\n\n### 8.1 Authentication\n- Alle API Routes müssen authentifizieren (außer public)\n- Auth-Check am Anfang der Route\n- JWT-Validation zentral in `@/lib/auth`\n\n### 8.2 Authorization\n- Check: Ist der User autorisiert, die Action auszuführen?\n- Admin-Only Routes zentral schützen\n- Checks auf User-IDs oder Permissions\n\n### 8.3 Validation\n- ALLE Benutzereingaben validieren\n- Server-side validation ist zwingend\n- Type-checking für API-Inputs\n\n# CODE REVIEW CHECKLIST\n\n- [ ] TypeScript ohne Fehler (`npm run build`)\n- [ ] ESLint nicht kritisch (`npm run lint`)\n- [ ] Alle `any` Types durch konkrete Types ersetzt\n- [ ] Keine Debug-Logs in Routes und Components\n- [ ] Konsistente Error-Handling (try-catch)\n- [ ] Auth-Prüfung für nicht-public Routes\n- [ ] Germane Translations inkl. Umlaute korrekt\n- [ ] Performance: DB-Queries optimisiert\n- [ ] No console.log in production code\n\n# RESOURCES\n\n- [TypeScript Handbook](https://www.typescriptlang.org/docs/handbook/intro.html)\n- [Next.js Documentation](https://nextjs.org/docs)\n- [Prisma Docs](https://www.prisma.io/docs)\n- [shadcn/ui Components](https://ui.shadcn.com)\n\n---\n\""
